---
title: Limitations
description: Things to know about this version.
---

- **Redis 6.2 or newer** is needed for `Bucket::replace` and `Bucket::take`.
- **Semaphore permits have no owner.** If a program crashes while it holds permits, they are lost until someone adds them back. Use `PermitExpirableSemaphore` with a lease when that matters.
- **Lost messages.** After a lost connection, a waiting program may miss the "unlocked" message. It then wakes up when the lease ends.
- **Dropping a guard without a runtime.** The lock cannot be released at once. It frees itself when the lease ends.
- **Redis Cluster.** `rename` can fail when the old and new names are in different hash slots. Redis itself does this.
- **RateLimiter.** `rename` is not supported. With `RateType::PerClient`, every client instance leaves two small keys behind. Call `expire` on the limiter to let them go away.
- **Numbers.** `HashMap::incr_by` needs values that the codec writes as plain numbers.
- **HashMap and Redisson's `RMap`.** There is no `mapReduce` (redissun has no executor service) and no `TrackingListener` (redissun does not use RESP3 client tracking). A failing `MapLoader` gives `Error::Loader`, where Redisson returns `null`. `keys_with` and the other pattern scans read the whole hash, while Redisson's `readAllKeySet(pattern)` reads only the first `HSCAN` page. Map events of different kinds can arrive out of order among themselves, and without subkey notifications (Redis 8.8 with `T`) a field event comes 50 ms after its write and without the key.
- **Write-behind.** A Redisson client and a redissun client do not share write-behind queues: redissun's queue is `{name}:redissun_write-behind-queue` with its own format, Redisson's holds Java-serialized tasks. An entry redissun cannot read is logged and skipped. After `rename` of a write-behind map, its task keeps polling the queue of the old name, as in Redisson. There is no `destroy()`: `flush()` and dropping the map's last handle drain the queue.
- **Equal values.** `Vec`, `VecDeque` and `HashSet` compare values by their encoded bytes. The codec must give the same bytes for equal values. The JSON codec does this for structs and numbers, but not for a `HashMap` inside a value, because its key order is random.
- **Collections.** `Vec::insert` and `Vec::remove` by index are O(n). Iteration reads pages, so changes made while you read can make you miss a value or see it twice.
- **Blocking pops** use their own short-lived connection. A pop that is dropped while an element is on its way can lose that element. Use `.timeout(wait)` for time limits.
- **Topic** does not store messages. A slow subscriber that falls more than 256 messages behind gets `Error::Lagged`. Use `ReliableTopic` when every message must arrive.
- **RwLock** does not prefer writers, and a reader cannot be upgraded to a writer.
- **FairLock** keeps a place in the queue for about 5 seconds per waiter ahead of it. A waiter that crashed is skipped after that. A waiter that is cancelled at the very moment its first attempt runs can leave a stale place that also ends after that time.
- **HashMapCache and Redisson's `RMapCache`.**
  - The background clean-up runs on the runtime that first created the cache.
  - Expiry uses each client's clock, as in Redisson, so keep the clocks of all clients in sync.
  - Events are always sent with `PUBLISH`, never with sharded pub/sub.
  - `set`, `entry` and `extend` without `.ttl()` clear an entry's time limits, like `insert`. Redisson's `fastPut`, `compute` and `putAll` keep them.
  - `incr_by` on an expired entry that the clean-up has not removed yet starts a new counter at the given amount, with no time limits. Redisson's `addAndGet` keeps the passed time limit there, so its value stays hidden until the clean-up deletes it.
  - `value_len` returns the length of the encoded value without the 16-byte header (12 on a Windows server) that Redisson's `valueSize` counts.
  - A write with limits into a full cache that overwrites a live key also drops one other entry, because Redisson's size check uses `>=`.
  - `peek` and the scans read from the master. Redisson may read them from a replica.
  - Not ported: `mapReduce`, `TrackingListener`, `destroy`, `sizeInMemory`, `expireAt` and `expire` with a condition, and `MapCacheOptions.removeEmptyEvictionTask`.
- **MapCacheNative and Redisson's `RMapCacheNative`** (experimental).
  - It needs Redis 7.4 or Valkey 9 (hash field expiration) for every method that sets or reads a time to live, and Redis 8.0 for the methods that send `HSETEX`: `extend(..).expire_at(t)`, `extend(..).keep_ttl()`, `try_extend` and `update_many`. On an older server they return `Error::Unsupported` and write nothing.
  - A client asks the server which hash field commands it has with `HPTTL` and `HSETEX` and keeps only a yes. In a cluster with mixed Redis versions that answer may not hold for every node: a TTL write that reaches an older node fails after its `HSET`, and the entry stays without a time to live.
  - `len` (`HLEN`) counts an expired entry until the server deletes it.
  - Plain writes (`insert`, `set`, `extend`, a write through `entry` without `.ttl()`) clear an entry's time to live (`HSET`), as in Redisson. `replace` and `compare_and_set` keep it, like `HashMapCache`; Redisson's `replace` and `replace(k, old, new)` clear it.
  - A zero TTL means none. Redisson's `expireEntry(k, Duration.ZERO)` deletes the entry; `expire_entry(&k).ttl(Duration::ZERO)` removes its TTL.
  - `entry_ttl` and `entry_ttls` give `None` both for a missing entry and for one without a time to live, where Redisson returns `-2` and `-1`.
  - The server deletes a field whose time ran out when it is read, or a little later on its own. Until then, `expire_entry` and `expire_entries` find it and give it the new time, as with Redisson.
  - It has no maximum size, no max idle, no entry events with values, no leases and no `updateEntryExpiration`, as in Redisson. Not ported, as on the other maps: `sizeInMemory`, `destroy`, `mapReduce`, `expireAt` and `expire` with a condition.
- **Multimaps and Redisson's `RListMultimap`, `RSetMultimap` and their `Cache` and `CacheNative` variants** (experimental).
  - `ListMultimapCacheNative` and `SetMultimapCacheNative` need Redis 7.4 or Valkey 9 only for `expire_key`; on an older server it returns `Error::Unsupported` and writes nothing. Every other method runs on Redis 6.2.
  - The index writes of a handle (`pop`, `remove(i)`, `trim`, `remove_value_n`, `remove_value_all`, `retain_values`, `HashSet` `retain`, and writes through `as_vec()`/`as_set()`) do not touch the hash, as in Redisson. A key they empty has `contains_key` `false` and no values, but `key_len` and `keys` count it until `remove_all` or `remove_many`.
  - `ListMultimap::remove_from_all_keys` never removes a key from the hash, as in Redisson, so a key whose list it empties is counted the same way.
  - `rename` renames the hash and every values key, so in a cluster it works only to a name in the same slot, such as `{t}:a` to `{t}:b`, or `a` to `{a}2`.
  - On the `Cache` types, `len`, `key_len`, `keys_to_vec`, `remove_from_all_keys` and the streams count an expired key until the clean-up task deletes it, as Redisson's unoverridden `size`, `keySize` and iterators do; reads of one key, the handles and `contains_value` hide it at once. The clean-up task first runs `eviction_interval` (5 s by default) after the multimap is first created in a client and then adapts its pause up to 30 minutes, so an expired key can be counted for that long.
  - On the `Cache` types, a put or replace over a key that has expired but that the clean-up has not deleted yet first deletes the key's old values and score, so the key starts clean with only the new values and no TTL, and `expire_key` on such a key returns `false` without reviving it. Redisson writes into the hidden values, loses them at the clean-up, and revives the old values on a later `expireKey`.
  - On the `Cache` types, deadlines are taken from the client's clock and compared with the client's clock, as in Redisson, so clients whose clocks disagree see a key expire at different times.
  - On the `Cache` types, the index writes of the handle (`set`, `insert`, `remove(i)`, `pop`, `trim`, …) and writes through `as_vec()`/`as_set()` ignore the key's TTL, as in Redisson; they can write to an expired key that the clean-up has not deleted yet. The handle's TTL-aware removals (`remove_value`, `remove_values`, `remove`, `retain`, …) do not take a key they empty out of the hash, as in Redisson.
  - On the `CacheNative` types, `replace_values` and `set_values` make the key permanent, as in Redisson; `extend` and `insert` keep its TTL.
  - On the `CacheNative` types, an index write or `remove_from_all_keys` can empty a list while the key's field keeps its TTL. A later push then makes a new list with no TTL, and when the field expires that list is left behind with no key in the hash. Redisson does the same.
  - In a cluster, a name with `{` but no valid hash tag (such as `a{b` or `{}x`) puts the values keys in another slot than the hash, so the scripts fail with `CROSSSLOT`, as in Redisson. Use a name with a real tag, such as `{t}:a`, or none.
  - Not ported, as on the other objects: `sizeInMemory`, `copy`, `renamenx`, `expireAt` and `expire` with a condition, `destroy` (the `Cache` types' clean-up task stops with the client), `mapReduce`, the distributed iterators of the handles, and `putAll(Multimap)`, which Redisson 4.8.0 does not have.
- **Gcra and Redisson's `RGcra`** (experimental).
  - No released Redis has the `GCRA` command (Redis held it out of 8.8.0 and later; only the `redis:8.8-m03` preview has it). On every other server redissun runs a Lua port with the same replies. Its state is a string that Redisson cannot use on that server (Redisson's script fails there with "unknown command"), and it gives `SET` keyspace events (the `$` class) instead of `gcra` events (the `r` class).
  - A client asks the server once whether it has `GCRA` and keeps the answer, so restart clients after moving to a server with `GCRA`. A cluster whose nodes differ, or a key used by both kinds of server, gives `WRONGTYPE` until the state key expires (`persist()` prevents that, a longer `expire()` delays it) or `set_rate` or `del` resets it.
  - `retry_after` and `full_burst_after` are whole seconds, rounded up by the server.
  - `exists`, `ttl` and `rename` cover the config key `{name}:config` too, where Redisson's look at the state key only; `ttl` is the config key's.
  - The deprecated `tryAcquire(maxBurst, tokensPerPeriod, period[, tokens])` is not ported.
- **LocalCachedMap and Redisson's `RLocalCachedMap`.** Not ported: `cacheSize(-1)`, a local cache that stores nothing (`cache_size(0)` means no limit, as in Redisson); `useObjectAsCacheKey`, since the local cache is always keyed by the encoded key; and `useTopicPattern`.
- **LocalCachedMapCache and Redisson's `RLocalCachedMapCache`.**
  - Writes by clients without a local cache (a plain `HashMapCache`, Redisson's `RMapCache`) are not announced, so local copies keep the old value until their lifetime ends; their removals and the server's evictions do reach the local caches.
  - Local hits do not count as uses on the server, so under `set_max_size` the entries read mostly from local caches look cold there and are evicted first.
  - Entry deadlines use the clocks of the clients that write, as in Redisson.
  - A sync or eviction message arrives a few milliseconds after the write, so another instance can read its old copy in between.
- **Short times.** Time limits and leases are rounded up to whole milliseconds. Zero is an error, except for the entry time limits of `HashMapCache` and `HashSetCache` and the entry TTLs of `MapCacheNative`, where zero means no limit. A `MapCacheNative` deadline (`.expire_at(t)`) is sent in whole Unix milliseconds, rounded down.
- **Before 1.0**, the API can change between minor versions.
