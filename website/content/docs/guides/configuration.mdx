```rust
use redissun::{Client, DelayStrategy};
use std::time::Duration;

let client = Client::builder()
    .url("redis://127.0.0.1:6379")
    .pool_size(8)
    .timeout(Duration::from_secs(3))
    .retry_attempts(4)
    .retry_delay(DelayStrategy::EqualJitter {
        base: Duration::from_secs(1),
        max: Duration::from_secs(2),
    })
    .reconnection_delay(DelayStrategy::EqualJitter {
        base: Duration::from_millis(100),
        max: Duration::from_secs(10),
    })
    .client_name("orders")
    .build()
    .await?;
```

## Settings

| Setting | Default | Redisson | Meaning |
|---|---|---|---|
| `url` | none, required | `address` | Redis address. Use `redis-sentinel://host:26379?sentinelServiceName=mymaster` for Sentinel and `redis-cluster://host:7000?node=host:7001` for Cluster. |
| `pool_size` | 4 | `connectionPoolSize` | number of connections |
| `database` | from the URL, else 0 | `database` | database number |
| `client_name` | none | `clientName` | name of every connection, shown by `CLIENT LIST` |
| `username`, `password` | from the URL | `username`, `password` | credentials for `AUTH` |
| `credentials_resolver` | none | `credentialsResolver` | async function that gives the credentials of each new connection |
| `credentials_refresh_interval` | none | `nextRenewal` | how often open connections ask the resolver again |
| `timeout` | 3 s | `timeout` | how long a command waits for its reply |
| `connect_timeout` | 10 s | `connectTimeout` | how long `build` and one connection attempt may take |
| `retry_attempts` | 4 | `retryAttempts` | how often a command is sent again after its connection failed |
| `retry_delay` | `EqualJitter` 1 s to 2 s | `retryDelay` | pause between two retries of a batch or a lock write |
| `reconnection_delay` | `EqualJitter` 100 ms to 10 s | `reconnectionDelay` | pause between two reconnection attempts |
| `ping_connection_interval` | 30 s | `pingConnectionInterval` | how often each connection is checked with `PING` |
| `keep_alive` | false | `keepAlive` | TCP keep-alive |
| `tcp_keep_alive_idle` | system | `tcpKeepAliveIdle` | idle time before the first keep-alive probe |
| `tcp_keep_alive_interval` | system | `tcpKeepAliveInterval` | pause between keep-alive probes |
| `tcp_no_delay` | true | `tcpNoDelay` | `TCP_NODELAY` |
| `lock_lease` | 30 s | `lockWatchdogTimeout` | lease for locks without their own lease |
| `check_lock_synced_replicas` | true | `checkLockSyncedSlaves` | fail a lock call when no replica got the write |
| `replicas_sync_timeout` | 1 s | `slavesSyncTimeout` | how long a lock write waits for replicas |
| `fair_lock_wait_timeout` | 5 min | `fairLockWaitTimeout` | how long a `FairLock` waiter keeps its place |
| `eviction_interval` | 5 s | `minCleanUpDelay` | first pause of the cache clean-up task |
| `reliable_topic_watchdog_timeout` | 10 min | `reliableTopicWatchdogTimeout` | how long a `ReliableTopic` subscriber that stopped renewing itself stays registered |
| `codec` | JSON | `codec` | how values are turned into bytes, see [Codecs](/docs/guides/codecs) |
| `check_slots_coverage` | true | `checkSlotsCoverage` | fail `build` for Redis Cluster while a slot has no master |
| `read_mode` | `Master` | `readMode` (default `SLAVE`) | where reads go, see [Reading from replicas](#reading-from-replicas) |
| `replica_scan_interval` | 5 s in a cluster, 1 s with Sentinel | `scanInterval` | how often the client looks for replicas again while it reads from them |
| `connection_listener` | none | `connectionListener` | told when a node gets connected and when it loses its connections, see [Connection events](#connection-events) |

## Credentials

A password in the URL works: `redis://user:password@host:6379`. `username` and `password` on the builder replace the ones in the URL, so the secret can stay out of the URL:

```rust
let client = Client::builder()
    .url("redis://redis.example.com:6379")
    .username("orders")
    .password(std::env::var("REDIS_PASSWORD")?)
    .build()
    .await?;
```

For passwords or tokens that change, give a resolver, like Redisson's `CredentialsResolver`. It gets the node's `host:port` and is asked for every new connection. With `credentials_refresh_interval` the open connections ask it again and send a new `AUTH`.

```rust
use redissun::Credentials;

let client = Client::builder()
    .url("redis://redis.example.com:6379")
    .credentials_resolver(|address| async move {
        let token = fetch_token_for(&address).await?;
        Ok(Credentials::new("orders", token))
    })
    .credentials_refresh_interval(Duration::from_secs(600))
    .build()
    .await?;
```

An error from the resolver fails the connection. `Debug` output never shows a password.

## Timeouts

`timeout` limits how long a command waits for its reply. The call then fails with an error. Blocking calls such as `pop_front_wait` or `read_group_wait` are not limited, because they wait on purpose. A lock write that waits for replicas gets `replicas_sync_timeout` on top. `Duration::ZERO` turns the limit off.

## Retries

When a connection fails while a command waits for its reply, the client reconnects and sends the command again, up to `retry_attempts` times. A write such as `incr` can then be applied twice. Commands that Redisson sends only once are never sent again: taking and releasing locks and permits, pushes and pops, `SETNX`-like writes, `HINCRBY`, `ZINCRBY`, `GEOADD`, `XADD` and the like.

A command is sent again as soon as its connection is back, so the pause before it is the `reconnection_delay`. `retry_delay` is the pause between two retries of a [Batch](/docs/objects/batch) and of a lock write that no replica confirmed.

## Delay strategies

| `DelayStrategy` | Redisson | Pause before retry `n` (from 0) |
|---|---|---|
| `Constant(d)` | `ConstantDelay` | always `d` |
| `EqualJitter { base, max }` | `EqualJitterDelay` | `e = min(base × 2ⁿ, max)`, then a random value between `e / 2` and `e` |
| `FullJitter { base, max }` | `FullJitterDelay` | `e = min(base × 2ⁿ, max)`, then a random value between 0 and `e` |
| `DecorrelatedJitter { min, max }` | `DecorrelatedJitterDelay` | a random value between `min` and `min + 3 × previous pause`, at most `max` |

## Connection checks

Every `ping_connection_interval` each pooled connection, the pub/sub connection and every idle batch connection get a `PING`. A connection that does not answer within `timeout` is closed and opened again. This finds connections that a firewall or a load balancer dropped without a word.

A command that waits longer than `timeout` fails with `Error::Timeout`, and its connection is checked by the next `PING`. Batches, blocking calls and the pub/sub connection wait on purpose: a batch waits `timeout` for its replies, a blocking call as long as it was asked to.

The pub/sub connection is opened when an object first needs it: a lock or semaphore that waits, a `Topic` subscriber, cache events, a `LocalCachedMap` or a `DelayedQueue`.

## Connection events

A `ConnectionListener` is told when a node gets connected and when it loses its connections, like Redisson's `ConnectionListener`. Both methods have empty defaults, so implement only the ones you need.

```rust
use redissun::{Client, ConnectionListener, NodeType};

struct Report;

impl ConnectionListener for Report {
    fn on_connect(&self, address: &str, node: NodeType) {
        println!("{node:?} {address} connected");
    }

    fn on_disconnect(&self, address: &str, node: NodeType) {
        println!("{node:?} {address} disconnected");
    }
}

let client = Client::builder()
    .url("redis://127.0.0.1:6379")
    .connection_listener(Report)
    .build()
    .await?;
```

- `address` is `host:port`. `node` is `NodeType::Master` (also for a single server), `Replica` (a replica that takes reads) or `Sentinel`.
- A node counts as connected from its first open connection until it has none left. A pool of several connections to one node is one `on_connect`, and one `on_disconnect` once all of them are gone.
- Redisson reports a disconnect when any one connection of the node closes. redissun waits for the last one, so a blocking command that closes its own connection is no event.
- A dropped client reports nothing more.
- The methods run on the task that opened or lost the connection. Keep them quick and hand longer work to another task.

## Reading from replicas

`read_mode` sends reads to replicas, like Redisson's `readMode`:

| `ReadMode` | Redisson | Reads go to |
|---|---|---|
| `Master` (default) | `MASTER` | the master |
| `Replica` | `SLAVE` | the replicas in turn, the master while there is none |
| `MasterAndReplica` | `MASTER_SLAVE` | the master and each replica in turn |

```rust
use redissun::ReadMode;

let client = Client::builder()
    .url("redis-cluster://127.0.0.1:7000?node=127.0.0.1:7001")
    .read_mode(ReadMode::Replica)
    .build()
    .await?;
```

A replica copies the master with a delay, so a read from it can miss a write made just before. That is why the default is `Master`, unlike Redisson, where it is `SLAVE`.

Reads are the plain commands that only look at data, the ones Redisson sends with `readAsync`: `get`, `len`, `contains`, ranges, ranks, scores and the like on `Bucket`, `BitSet`, `Geo`, `HashMap`, `HashSet`, `SortedSet`, `Vec` and `VecDeque`, and `exists` and `ttl` on every object. These always use the master, as in Redisson:

- writes, and reads inside a write such as `insert` returning the old value,
- `AtomicI64::get`, `AtomicF64::get`, `HyperLogLog` counts, `SortedSet` random members and `HashSet::intersection_len`,
- scans (`iter`), whose cursor must stay on one node,
- scripts, batches, blocking calls and pub/sub,
- locks, semaphores, latches, rate limiters and the other coordination objects, which must see their own last write,
- `LocalCachedMap::get` and `contains_key`, which would otherwise cache a stale value, and `HashMapCache` and `HashSetCache`, whose reads are scripts.

Replicas are the ones `CLUSTER SLOTS` lists in Redis Cluster and the ones Sentinel reports with `SENTINEL REPLICAS`, leaving out, as Redisson does, those it marks `s_down` or `disconnected` and those whose link to the master is in error. The client looks for them again every `replica_scan_interval`. Redis Cluster lists a replica only once it has copied some data, so in a new cluster reads move to the replicas within a few seconds of the first writes. A single server has no replicas, as Redisson's single server mode has no `readMode`.

Each replica gets a pool of `pool_size` connections when the first read goes to it; in Redis Cluster they send `READONLY`. A read that a replica cannot answer, because it is down, loading its data or no longer serves the slot, goes to the master.

## Tuning

The defaults suit most programs, and on a real network the round trip costs far more than any of these settings save. [Benchmarks](/docs/guides/benchmarks) on one machine showed no gain from more connections than the default 4.

- `pool_size`: more connections help when many tasks send large values at once. One connection already carries many commands at a time, because commands are pipelined.
- `timeout` and `retry_attempts`: a command that is not answered fails after `timeout`, and one whose connection failed is sent again up to `retry_attempts` times. Commands that must not run twice, such as a lock or a pop, are sent once.

```rust
let client = Client::builder()
    .url("redis://127.0.0.1:6379")
    .pool_size(8)
    .timeout(Duration::from_secs(1))
    .retry_attempts(2)
    .build()
    .await?;
```

## TLS

TLS needs the `tls-rustls` feature:

```toml
[dependencies]
redissun = { version = "0.22", features = ["tls-rustls"] }
```

Then use a `rediss://` URL. Sentinel and Cluster work the same way with `rediss-sentinel://` and `rediss-cluster://`. The sentinels, the masters, the replicas and the cluster nodes must all speak TLS.

```rust
use redissun::{Client, TlsVerification};

let client = Client::builder()
    .url("rediss://redis.example.com:6380")
    .tls_ca_file("/etc/redis/ca.pem")
    .tls_client_auth_files("/etc/redis/client.pem", "/etc/redis/client.key")
    .tls_verification(TlsVerification::Strict)
    .build()
    .await?;
```

| Setting | Redisson | Meaning |
|---|---|---|
| `tls_ca_pem(pem)`, `tls_ca_file(path)` | `sslTruststore` | trust only the CA certificates in this PEM data. Without it the system's certificates are trusted. |
| `tls_client_auth_pem(chain, key)`, `tls_client_auth_files(chain, key)` | `sslKeystore` | the client certificate chain and key, as PEM, for servers with `tls-auth-clients yes` |
| `tls_verification(mode)` | `sslVerificationMode` | how the server certificate is checked |

| `TlsVerification` | Redisson | Checks |
|---|---|---|
| `Strict` (default) | `STRICT` | the certificate is signed by a trusted CA and names the host in the URL |
| `CaOnly` | `CA_ONLY` | the certificate is signed by a trusted CA. Use it when Sentinel or Cluster report IP addresses that the certificate does not name. |
| `None` | `NONE` | nothing. The traffic is encrypted, but anyone in the middle can read it. Only for tests. |

Files are read when you call `build()`. A missing file or bad PEM data is an `Error::Config`. A `rediss://` URL without a TLS feature is an `Error::Config` too, so a client never falls back to plain text.

`tls-rustls` uses rustls with the `ring` crypto provider. If your program already uses rustls with `aws-lc-rs`, turn on `tls-rustls-aws-lc` instead, so only one provider is built. When your program installs a default rustls `CryptoProvider`, redissun uses it.
