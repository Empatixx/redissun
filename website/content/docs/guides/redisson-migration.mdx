---
title: Migrating from Redisson
description: redissun is Redisson for Rust. How Redisson's objects, names, settings and behaviour map to redissun.
---

redissun is Redisson for Rust: the same objects, data layout and Lua scripts, with Rust names where Rust has a type. This page maps Redisson's classes, methods and settings to redissun.

## Vec

Redisson's `range(a, b)` and `trim(a, b)` include both ends. In redissun they take a Rust range, so use `a..=b`.

## SortedSet

Redisson's rank ranges include both ends; redissun takes any Rust range, so `valueRange(a, b)` is `range(a..=b)`. Score ranges take any `f64` range, which covers Redisson's inclusive flags. Iteration uses `ZSCAN`, as in Redisson, so its order is not guaranteed.

| Redisson | redissun |
|---|---|

| `addAll(map)` | `extend(entries)` |

| `addAndGetRank`, `addAndGetRevRank` | `insert_and_rank`, `insert_and_rev_rank` |

| `getScore(v)`, `getScore(list)` | `score(&v)`, `scores(&list)` |
| `rank(v)`, `revRank(v)`, `rankEntry(v)` | `rank(&v)`, `rev_rank(&v)`, `rank_with_score(&v)` |

## ReliableTopic and ShardedTopic

They map like `Topic`. A `ReliableTopic` also has `len()` (Redisson's `size()`), and each `client.reliable_topic(name)` handle is one subscriber, as each `getReliableTopic` call is in Redisson.

## Behavioural differences

- The lock owner is a client and a tokio task, not a thread.
- Unlocking goes through a guard value. Unlocking something you do not hold is `Error::LockNotHeld` instead of an `IllegalMonitorStateException`.
- `Vec::remove(i)` past the end is `Error::OutOfRange`, also for index 0. Redisson returns `null` for index 0.
- Values use a serde codec rather than Redisson's Java codecs, so data written with Redisson's default codec is not readable by redissun and the other way round. With `StringCodec` on both sides, plain text values are shared.
- When a semaphore or latch changes, redissun wakes every waiter and each one tries again. Redisson wakes only as many as there are permits.
