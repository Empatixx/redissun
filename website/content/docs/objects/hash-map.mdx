---
title: HashMap
description: A shared map that works like HashMap.
---

A `HashMap` keeps its entries in a Redis hash. Keys and values both go through the codec.

```rust
let users = client.hash_map::<String, User>("users");

users.insert("jirka", &user).await?;
let found = users.get("jirka").await?;
```

Everything you send to Redis is borrowed: `users.insert("jirka", &user)` takes a `&str` key and a reference to the value, so you keep `user` and do not need `.into()` or `.clone()`. The values you get back are owned.

This differs from `HashMap::insert`, which takes ownership. redissun only encodes the data and sends it, so it never needs to own it.

## Methods

| Method | Redis command | Notes |
|---|---|---|
| `insert(k, v)` | Lua script | returns the old value |
| `get(&k)` | `HGET` | |
| `remove(&k)` | Lua script | returns the removed value |
| `contains_key(&k)` | `HEXISTS` | |
| `len()` and `is_empty()` | `HLEN` | |
| `clear()` | `DEL` | |
| `extend(entries)` | `HSET` | entries are `(&key, &value)` pairs, for example `map.extend(other.iter())`. One request, or one per `n` entries with `.batch_size(n)`. An empty list does nothing. |
| `to_hash_map()` | `HGETALL` | the whole map at one moment |
| `random_entries(n)` | `HRANDFIELD … WITHVALUES` | |
| `entry(&k)` | under the key's lock | see below |
| `lock(&k)` and the other per-key objects | | see below |
| `events()` | keyspace notifications | see below |
| `get_many(&[&k])` | `HMGET` | same order as the keys |
| `set(k, v)` | `HSET` | does not read the old value; `true` if the key was new |
| `try_insert(k, v)` | Lua script | stores only a missing key; `None` if it stored it, else the present value |
| `replace(k, v)` | Lua script | changes only a present key; returns the old value |
| `compare_and_set(k, old, new)` | Lua script | changes the value only while it is `old` |
| `remove_if_eq(k, v)` | Lua script | removes the entry only while its value is `v` |
| `remove_many(&[&k])` | `HDEL` | how many were present |
| `contains_value(&v)` | Lua script | reads every value on the server |
| `value_len(&k)` | `HSTRLEN` | bytes of the encoded value |
| `random_keys(n)` | `HRANDFIELD` | |
| `incr_by(&k, delta)` | `HINCRBY` | a missing entry starts at zero |
| `incr_by_float(&k, delta)` | `HINCRBYFLOAT` | |

`incr_by` and `incr_by_float` need values that the codec writes as plain numbers. Integers and floats do this with the JSON codec.

## Read all entries

`iter`, `keys` and `values` return a `Stream`. They use `HSCAN` and read 100 entries at a time. The whole map is never loaded at once.

```rust
use futures::TryStreamExt;

let entries: Vec<(String, User)> = users.iter().try_collect().await?;
```

`iter_with`, `keys_with` and `values_with` take a `MapScan` with a pattern and a page size. The pattern is matched against the encoded key, as in Redisson: with the JSON codec the key `abc` is stored as `"abc"`, so keys starting with `a` match `"a*`.

```rust
use redissun::MapScan;

let some: Vec<String> = users
    .keys_with(MapScan::new().pattern("\"j*").page_size(500))
    .try_collect()
    .await?;
```

## Entries

`entry(&k)` takes the key's lock, reads the value and returns an `Entry`, like `std::collections::hash_map::Entry`. It replaces Redisson's `compute`, `computeIfAbsent`, `computeIfPresent` and `merge`. The lock is the one a Redisson client takes for those, so two programs never change the same key at once.

```rust
let visits = client.hash_map::<String, i64>("visits");
visits.entry("home").await?.and_modify(|n| *n += 1).or_insert(1).await?;
```

`and_modify` changes the value in memory and `or_insert`, `or_insert_with` or `or_default` writes it. Match on `Entry::Occupied` and `Entry::Vacant` (from `redissun::hash_map`) to `insert` or `remove` instead. The lock is released when the entry is consumed; an entry you drop writes nothing and releases it in the background.

Entries for the same key taken in one program, even by futures joined in one task, wait for each other. Do not take a second entry for a key while you hold one in the same task: it waits forever.

## Per-key locks and synchronizers

`lock(&k)`, `fair_lock`, `rw_lock`, `semaphore`, `count_down_latch` and `permit_expirable_semaphore` return the object Redisson's `getLock(key)` and friends return, under the same name in Redis. A Java service and a Rust service locking the same key of the same map exclude each other.

## Events

`events()` returns `MapEvents`. Call `recv()` for the next `MapEvent`, or `into_stream()` for a `Stream` of them. The kinds are `Put`, `Incremented`, `Removed`, `Deleted` and `Expired`. `events_of(&[MapEventKind::Removed])` listens to some kinds only. Redis sends these events only when `notify-keyspace-events` enables them: `Eh` for field events, `g` for deletes, `x` for expiry. With `T` (Redis 8.8 or newer) the events name the changed key; otherwise `key` is `None`, as in Redisson.

## Loader and writer

`client.hash_map_builder::<K, V>(name)` sets options, then `.build().await` returns the map. See [Loaders and writers](/docs/guides/loaders-and-writers).

| Option | Default | Redisson |
|---|---|---|
| `.loader(l)` | none | `MapOptions.loader`, `loaderAsync` |

| Method | Notes |
|---|---|
| `load_all()` | loads every key of the loader; `.parallelism(n)`, `.replace_existing()` |
| `load_many(&[&k])` | loads those keys |

With a loader, `get`, `get_many`, `contains_key` and `entry` ask it on a miss.

## Missing keys and null values

`get` returns `None` for a missing key. If your value type is an `Option`, a stored `None` comes back as `Some(None)`. So you can tell the two cases apart.
