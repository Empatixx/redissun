---
title: SetMultimap
description: A map whose keys each hold a set of values, Redisson's RSetMultimap, RSetMultimapCache and RSetMultimapCacheNative. Experimental.
---

**Experimental.** A `SetMultimap` maps each key to a set of values. A key holds each value at most once; values are equal when their encoded bytes are equal. It is Redisson's `RSetMultimap`, with the same data in Redis, so Java and Rust clients share it.

```rust
let tags = client.set_multimap::<String, String>("tags");

tags.insert("post-1", "rust").await?;
tags.insert("post-1", "redis").await?;
let all = tags.get_all("post-1").await?; // "rust" and "redis", in no particular order
```

## Methods

| Method | Redisson | Notes |
|---|---|---|
| `insert(&k, &v)` | `put` | adds the value; `true` when it was new for the key |
| `get_all(&k)` | `getAll` | the values in no particular order (a `Vec`), empty for a missing key |
| `contains_key(&k)` | `containsKey` | whether the key has any values |
| `len()` | `size` | the values under all keys |
| `key_len()` | `keySize` | the keys (`HLEN`) |
| `is_empty()` | `isEmpty` | `len() == 0` |
| `extend(&k, values)` | `putAll(key, values)` | `true` when any value was new |
| `remove(&k, &v)` | `remove(key, value)` | the key goes with its last value |
| `remove_all(&k)` | `removeAll` | removes the key and returns its values |
| `replace_values(&k, values)` | `replaceValues` | returns the old values |
| `set_values(&k, values)` | `fastReplaceValues` | replaces without reading the old values |
| `remove_many(&[&k, ..])` | `fastRemove` | how many of the keys were there |
| `remove_from_all_keys(&[&v, ..])` | `fastRemoveValue` | removes each value from every key, and a key it empties; how many were removed |
| `contains_value(&v)`, `contains_entry(&k, &v)` | `containsValue`, `containsEntry` | |
| `keys_to_vec()` | `readAllKeySet` | every key (`HKEYS`) |
| `clear()` | `clear`, `delete` | deletes the hash and every set |
| `lock(&k)`, `fair_lock(&k)`, `rw_lock(&k)`, `semaphore(&k)`, `count_down_latch(&k)`, `permit_expirable_semaphore(&k)` | `getLock(key)`, … | the objects Redisson keeps per key, under the same names |

## Empty inputs

`extend(&k, [])` sends nothing and returns `false`, so no key is left without values (Redisson's script would add the key to the hash). `replace_values(&k, [])` and `set_values(&k, [])` remove the key, the first returning its old values. `remove_many(&[])` and `remove_from_all_keys(&[])` send nothing and return `0`.

## Streams

| Method | Redisson | Yields |
|---|---|---|
| `iter()`, `iter_paged(n)` | `entries()`, `entries(count)` | every `(key, value)` pair |
| `keys()`, `keys_paged(n)` | `keySet()`, `keySet(count)` | every key |
| `values()`, `values_paged(n)` | `values()`, `values(count)` | every value of every key |

```rust
use futures::TryStreamExt;

let pairs: Vec<(String, String)> = tags.iter().try_collect().await?;
```

The keys are read with `HSCAN … COUNT n`, `n` being the page size (10 by default, as in Redisson; `0` means 10). The values of each key are read with `SSCAN … COUNT n`. Keys without values yield nothing in `iter` and `values`. Like every scan, a stream may miss or repeat entries that change while it runs.

## Values of one key

`get(&k)` returns a `SetMultimapValues` handle on the set of the key, Redisson's `get(key)`. It is lazy: building it sends nothing, and each method is one request.

```rust
let post = tags.get("post-1")?;
post.insert("tokio").await?;
let has_both = post.contains_all(&["rust", "tokio"]).await?;
```

| Method | Redisson | Through |
|---|---|---|
| `insert(&v)`, `extend(values)` | `add`, `addAll` | the multimap's `insert`/`extend`, so a new key joins the hash; `extend` returns how many values were new |
| `remove(&v)`, `remove_values(&[&v, ..])` | `remove`, `removeAll` | the multimap scripts; the key goes with its last value |
| `clear()` | `delete` | `remove_many` of the key |
| `contains(&v)`, `contains_all(&[&v, ..])`, `len()`, `is_empty()`, `to_vec()`, `iter()` | `contains`, `containsAll`, `size`, `isEmpty`, `readAll`, `iterator` | reads of the set |
| `retain(&[&v, ..])` | `retainAll` | writes to the set only |

`as_set()` returns the raw [`HashSet`](./hash-set) on the values key for the rest of `RSet` (set algebra, `pop`, `random`, `move_to`, …). Writes through it do not add the key to the multimap, as with Redisson's inherited `RSet` methods. `name()` is the name of the set.

`retain` and writes through `as_set()` do not touch the hash, as in Redisson. When one empties the set, `contains_key` is `false`, `get_all` is empty and the streams skip the key, but `key_len` and `keys` count it until `remove_all` or `remove_many`.

## Events

`events()` listens to every change, `events_of(&[MultimapEventKind::ValueAdded, ..])` to some. Both return a `MultimapEvents`; `recv()` waits for the next `MultimapEvent`, `into_stream()` turns it into a stream, and dropping it stops listening (Redisson's `removeListener`).

| Event | Redis event | Redisson listener |
|---|---|---|
| `Put { key }` | `hset` on the hash: a write of the key's field, for a new key and for an existing one | `MapPutListener` |
| `Removed { key }` | `hdel` on the hash (a key went) | `MapRemoveListener` |
| `ValueAdded { name }` | `sadd` on a set of the multimap | `SetAddListener` |
| `ValueRemoved { name }` | `srem` on a set of the multimap | `SetRemoveListener` |
| `Deleted` | `del` of the hash | `DeletedObjectListener` |
| `Expired` | `expired` of the hash | `ExpiredObjectListener` |

```rust
let mut events = tags.events().await?;
tags.insert("post-1", "rust").await?;
let event = events.recv().await?; // Put or ValueAdded, in either order
```

Redis sends these only when `notify-keyspace-events` enables them, as for Redisson: `E` with `h` for `Put` and `Removed`, `s` for the value events, `g` for `Deleted`, `x` for `Expired`. `key` is `Some` only with `T` (Redis 8.8 or newer), otherwise `None`, as Redisson's listeners get `null`. `name` is the set's name, `{name}:<hash>`; value events of other keys are dropped by that prefix, as in Redisson. The prefix test is Redisson's `startsWith`, so listening on `m` also hears the values keys of a multimap named `{m}:x`. `Put` fires whenever a put writes the key's field, so it comes for an existing key too, not only when a key is added. Events of different kinds come from different subscriptions and may arrive in another order than the writes. In a cluster the listener hears the node of the client's pub/sub connection.

## Object methods

The `Object` methods cover the hash and the set of every key, with Redisson's scripts:

| Method | Redisson | Notes |
|---|---|---|
| `del()` | `delete` | deletes the hash and every set; `true` when anything was deleted |
| `expire(ttl)` | `expire` | sets the TTL on the hash and every set |
| `persist()` | `clearExpire` | clears the TTL of every set; returns whether the hash had one |
| `rename(new)` | `rename` | renames the hash and every set; fails when the multimap does not exist |
| `exists()`, `ttl()` | `isExists`, `remainTimeToLive` | read the hash |

The scripts name the sets from the hash, so in a cluster `rename` works only to a name in the same slot, for example `{t}:a` to `{t}:b`, or `a` to `{a}2`. Every other method runs on a cluster: the values keys share the slot of the name.

## Cache

**Experimental.** `client.set_multimap_cache(name)` returns a `SetMultimapCache`, Redisson's `RSetMultimapCache`. It is a `SetMultimap` with the same data and methods, plus `expire_key`, which gives one key a deadline. The deadlines live in Redisson's ttl zset `{name}:redissun_set_multimap_ttl` (members are the encoded keys, scores Unix milliseconds), so it runs on Redis 6.2:

```rust
use std::time::Duration;

let carts = client.set_multimap_cache::<String, String>("carts");
carts.insert("user-1", "book").await?;
carts.expire_key("user-1", Duration::from_secs(600)).await?; // true: the key exists
```

| Method | Redisson | Notes |
|---|---|---|
| `expire_key(&k, ttl)` | `expireKey(key, ttl, unit)` | records now + `ttl` as the key's score; `false` for a missing key |
| `expire_key(&k, Duration::ZERO)` | — | removes the key's score, so the key no longer expires |

- The deadline is taken from the client's clock, as in Redisson, and the scripts compare it with the client's clock too. Clients whose clocks disagree see a key expire at different times.
- Reads of one key hide an expired key at once: `get_all`, `contains_key`, `contains_entry` and the handle from `get`, and also `contains_value`. `len`, `key_len`, `keys_to_vec`, `remove_from_all_keys` and the streams count an expired key until the clean-up task deletes it, as Redisson's unoverridden `size`, `keySize` and iterators do.
- Writes to a live key keep its deadline. A key that is new to the hash starts without one: redissun's put scripts drop a stale score left by `remove`, `remove_many` or `remove_from_all_keys`, which Redisson's do not, so in Redisson such a key can read as expired at once.
- `remove_all` drops the key's score, as in Redisson.
- A background task deletes expired keys, Redisson's `MultimapEvictionTask`: each run takes up to 100 keys whose deadline passed and deletes their sets, their fields and their scores. It starts when `client.set_multimap_cache(name)` is first called for the name (one task per name and client), first runs after [`eviction_interval`](/docs/guides/configuration) (5 s by default), and adapts its pause between that interval and 30 minutes, as Redisson does. It stops with the client. Every client runs its own task and there is no lock between them, as in Redisson; each run is one atomic script, so that is harmless. redissun's script builds the set names like `suffix_name`, so a name with a hash tag, such as `{t}:carts`, is cleaned too; Redisson's misses its sets and fails on a cluster.
- `Object::del`, `expire` and `persist` cover the ttl zset too, with Redisson's scripts. `rename` renames the ttl zset with the rest, so key TTLs survive it; Redisson's cache does not, and drops them.

## CacheNative

**Experimental.** `client.set_multimap_cache_native(name)` returns a `SetMultimapCacheNative`, Redisson's `RSetMultimapCacheNative`. It is a `SetMultimap` with the same data and methods, plus `expire_key`, which gives one key a time to live with Redis 7.4 hash field expiry:

```rust
use std::time::Duration;

let sessions = client.set_multimap_cache_native::<String, String>("sessions");
sessions.insert("user-1", "tab-a").await?;
sessions.expire_key("user-1", Duration::from_secs(60)).await?; // true: the key exists
```

| Method | Redisson | Notes |
|---|---|---|
| `expire_key(&k, ttl)` | `expireKey(key, ttl, unit)` | `HPEXPIRE` on the key's hash field and `PEXPIRE` on its set, so both expire together; `false` for a missing key |
| `expire_key(&k, Duration::ZERO)` | — | clears both TTLs (`HPERSIST` + `PERSIST`); Redisson's `hpexpire 0` would delete the field and leave the set behind |

- Only `expire_key` needs Redis 7.4 or newer (or Valkey 9). On an older server it fails with `Error::Unsupported` before writing anything; every other method runs on Redis 6.2.
- When a key expires, the server removes its field and its set, so `len`, `key_len`, `contains_key` and `get_all` all show it gone.
- `extend`, `insert` and the handle's writes keep a key's TTL. redissun's `extend` uses `hsetnx` where Redisson's script uses `hset`, which would clear the field's TTL while the set kept its own.
- `replace_values` and `set_values` make the key permanent, as in Redisson: their scripts rewrite the field and recreate the set.
- `Object::expire` and `persist` work on the whole multimap, as on the plain type.

## How it is stored

Redisson's layout:

- A hash at the name maps each encoded key to `Hash.hash128toBase64` of the encoded key (a 22-character string, stored as is, not encoded). With `JsonCodec` the key `"key"` maps to `IKm9EBQhlzpVIBxUXDHBWw`.
- The values of a key live in the set `{name}:<hash>`, or `name:<hash>` when the name already has a `{`. So every key of the multimap is in the slot of the name, also in a cluster, as long as a name with `{` has a valid hash tag. A name like `a{b` or `{}x` has no tag: the hash's slot comes from the whole name and the values keys' slot from another string, so in a cluster the scripts fail with `CROSSSLOT`, as in Redisson.
