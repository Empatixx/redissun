---
title: ReliableTopic
description: A topic that keeps its messages in a stream until every subscriber has read them.
---

A `ReliableTopic` sends messages to every subscriber, like a [`Topic`](./topic), but keeps them in a Redis stream until each subscriber has read them, like Redisson's `RReliableTopic`. A subscriber that loses its connection or is slow gets every message once it reads again.

```rust
let events = client.reliable_topic::<String>("events");

let mut subscriber = events.subscribe().await?;
events.publish("deployed").await?;
let message = subscriber.recv().await?;
```

## Methods

| Method | Notes |
|---|---|
| `publish(&m)` | returns how many subscribers the topic has |
| `subscribe()` | returns a `ReliableSubscriber` with `recv()` and `into_stream()` |
| `size()` | the messages in the stream, read or not |
| `subscriber_count()` | the subscribers in all programs |
| `listener_count()` | the `ReliableSubscriber`s of this handle |
| `remove_all_listeners()` | ends the subscribers of this handle and removes it |

## Subscribers

Each handle from `client.reliable_topic(name)` is one subscriber: a consumer group of the stream. All the `ReliableSubscriber`s of a handle and its clones share it, and each of them gets every message. Two handles of the same name are two subscribers, as two calls of Redisson's `getReliableTopic` are.

A new subscriber first reads the messages that are still in the stream, then the new ones. After each batch, the stream is trimmed to the messages that some subscriber still has to read. As in Redisson, it is trimmed up to the millisecond of the oldest last-read message, so messages published in that same millisecond stay until a later batch.

A subscriber renews itself every third of the client's `reliable_topic_watchdog_timeout`, 10 minutes by default. When its program stops without dropping it, the other subscribers remove it after that time, and its unread messages with it. Dropping the last `ReliableSubscriber` of a handle removes the subscriber at once.

A `ReliableSubscriber` that reads slower than messages arrive holds back the others of its handle after 256 waiting messages; nothing is dropped.

## Good to know

- A message is acknowledged once it is handed to the subscribers of the handle. If the program stops before a subscriber reads it, it is not read again.
- Messages live in the stream named like the topic, under the field `m`. The subscribers live in the sorted set `{name}:timeout`. `del`, `expire` and `rename` change both.
