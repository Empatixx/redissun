---
title: Batch
description: Send many commands in one round trip.
---

A `Batch` collects commands from several objects and sends them to Redis together. This saves a network round trip for every command.

```rust
let batch = client.batch();

let visits = batch.atomic_i64("visits").incr();
let users = batch.hash_map::<String, String>("users");
let jirka = users.get("jirka");
users.insert("ann", "Ann");

batch.execute().await?;

let visits = visits.await?;
let jirka = jirka.await?;
```

Objects from a batch do not talk to Redis. Their methods queue a command and return a `BatchFuture`. After `execute()` each handle gives the typed reply, for example `Option<String>`. Commands run in the order you queued them. If you await a handle before `execute()`, it waits for an execution that did not start.

## Modes

| Call | Redisson | Meaning |
|---|---|---|
| (default) | `IN_MEMORY` | the commands are held in memory and pipelined. Other clients' commands can run between them. |
| `.atomic()` | `IN_MEMORY_ATOMIC` | held in memory and run in one `MULTI`/`EXEC` per Redis node on a connection only this batch uses, so nothing runs between the commands of a node |
| `.stored_in_redis()` | `REDIS_WRITE_ATOMIC` | each command is sent to Redis when you queue it and waits in a `MULTI` transaction per node on a connection only this batch uses. `execute()` runs `EXEC`. Nothing is held in memory, and nothing is applied if you drop the batch. |

As in Redisson, a command that Redis rejects fails its own handle and makes `execute()` return that error. The other handles still get their replies. Redis does not roll back a transaction, so the other commands are applied in every mode. `REDIS_READ_ATOMIC` is the same as `stored_in_redis` but reads from a replica. redissun does not route reads to replicas, so there is no separate read mode.

## Options

| Call | Meaning |
|---|---|
| `.skip_result()` | the handles do not get the replies and resolve to `Error::Config`. If a command failed, `execute()` still returns that error. |
| `.response_timeout(time)` | how long one attempt waits for Redis before it is retried or fails with `Error::Timeout`. With `sync` the sync timeout is added. Default is the client's `timeout`, 3 seconds unless changed, as in Redisson. |
| `.retry_attempts(n)`, `.retry_delay(strategy)`, `.retry_interval(time)` | send the batch again when the connection fails or the response times out. A retried write can be applied twice. Defaults are the client's `retry_attempts` and `retry_delay`: 4 retries with a pause that grows from about 0.5 to 2 seconds with random jitter, as in Redisson. `retry_interval` sets a fixed pause. Not used by `stored_in_redis`. |
| `.sync(slaves, timeout)` | after the commands, wait on every node the batch wrote to until `slaves` replicas have them (`WAIT`). `BatchResult::synced_slaves` is the sum over the nodes. |
| `.sync_aof(local, slaves, timeout)` | the same with `WAITAOF`, which also waits for fsync. Needs Redis 7.2. |

`execute()` returns a `BatchResult` with the number of `commands` and `synced_slaves`. `discard()` throws the queued commands away, and their handles resolve to `Error::Config`. If you drop a batch without executing it, the handles do the same. If you do not need a reply, `drop` the handle.

## What can be queued

| Object | Methods |
|---|---|
| `hash_map` | `insert`, `get`, `remove`, `contains_key`, `len` |
| `bucket` | `set`, `set_ex`, `get` |
| `hash_set` | `insert`, `remove`, `contains`, `len` |
| `atomic_i64` | `get`, `set`, `incr`, `decr`, `add_and_get` |
| `vec` | `push`, `get`, `len` |
| `vec_deque` | `push_back`, `push_front`, `pop_front`, `pop_back`, `len` |
| `sorted_set` | `insert`, `add_score`, `score`, `remove`, `len` |
| `topic` | `publish` |
| any key | `batch.del(name)`, `batch.expire(name, ttl)` |

Operations that wait, take a lock or need several steps are not available in a batch. In Redis Cluster an atomic batch can span nodes, but the keys on one node must share a hash slot, because Redis refuses a transaction that spans slots.
