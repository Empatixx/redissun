# 3: Multimaps (Redisson `RListMultimap`, `RSetMultimap` and their `Cache`/`CacheNative` variants): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Six new, experimental objects: `ListMultimap`, `SetMultimap`, `ListMultimapCacheNative`, `SetMultimapCacheNative` (PR 3a) and `ListMultimapCache`, `SetMultimapCache` (PR 3b). Together they cover every method of Redisson 4.8.0's `RMultimap`, `RListMultimap`, `RSetMultimap`, `RMultimapCache`, `RListMultimapCache`, `RSetMultimapCache`, `RListMultimapCacheNative` and `RSetMultimapCacheNative` (checked with `javap`). They use Redisson's data layout and Lua, so Java and Rust clients share the data. Each has lazy per-key value handles (`ListMultimapValues`, `SetMultimapValues`), streams, events, per-key locks and `Object` over all their keys.

**Architecture:** One private module `src/collections/multimap/` holds the shared code. A private `Shape::{List, Set}` picks the values type. A private `Mode::{Plain, Cache { timeout }, Native}` picks the TTL scheme. Both are plain enums inside the structs and never appear in a public bound. All operations live in a private `Ops<'_, C>` that matches on `(Shape, Mode)` to pick Redisson's script or command. A declarative macro `multimap_type!` generates the six public structs and their methods as one-line calls into `Ops`. This mirrors `RedissonMultimap` → `RedissonListMultimap`/`RedissonSetMultimap` → `…Cache`/`…CacheNative`. The two handles share a private `Slot` (map key, encoded key, key hash, mode). In plain and native mode they route the multimap writes through the multimap scripts, as Redisson's `InnerList`/`InnerSet` do, and their reads go to the existing `crate::Vec`/`crate::HashSet` on the values key. In cache mode they run the TTL-aware scripts of `RedissonListMultimapValues`/`RedissonSetMultimapValues`. Lua is copied verbatim into `multimap/scripts.rs`, apart from the deviations recorded below.

**Tech Stack:** Rust 2024, tokio, redis-rs, futures `Stream`, testcontainers (Redis 7.2 for the unsupported path, 7.4, a 7.4 Cluster).

**Spec:** `docs/superpowers/specs/2026-11-26-redisson-4x-objects-design.md`: "### 3. Multimaps", the 0-section bullet on multimaps, "API conventions", "Constraints", "Testing". The naming rules of `docs/superpowers/specs/2026-11-27-rust-idiomatic-api.md` replace the spec's naming lines. Builds on `HashMap`/`HashMapCache`/`MapCacheNative` and the shared `src/collections/map/*` (`key_hash`, `events`, `scan`), `map_cache_native/support.rs` (field-TTL probe) and `src/eviction.rs`.

**Branches:** PR 3a `feat/multimaps`, from `main` after `feat/gcra` is merged. PR 3b `feat/multimap-cache`, from `main` after PR 3a is merged.

## Owner decisions (from the brief, 2026-11-27)

1. Six objects. Rust names close to std and the `multimap` crate, mapped by the naming rules: `insert`, `get`, `get_all`, `remove`, `remove_all`, `contains_key`, `contains_value`, `contains_entry`, `len`, `key_len`, `keys`, `values`, `iter` (streams), `replace_values`, `extend`, and `fastRemove` → the crate name.
2. Shared code through a private enum or macro. No private traits in public bounds.
3. Key-level TTL on the cache variants is `expire_key(&k, d)`, Redisson's `expireKey`. The native variants use Redis 7.4 field expiry.
4. Every Redisson method is covered and carries a doc alias. Lua is verbatim. `Object` covers every key, including the per-key value lists/sets. Cluster hash tags are kept.
5. Up to two PRs, split by the builder (decision below).

## Decisions (mine, by the rules: Rust-idiomatic, Redisson parity, same name ⇒ same behaviour)

- **PR split: 3a = plain + native, 3b = cache.** `RedissonList/SetMultimapCacheNative extends RedissonList/SetMultimap` and overrides only `expireKey`, `expire`, `expireAt` and `clearExpire`. Its `get` returns the plain `InnerList`/`InnerSet`. So native is plain plus one script and the field-TTL probe (about 10% of the code). The cache variants bring their own ~25 scripts, Redisson's eviction task and a TTL-aware flavour of both handles, which is most of the review risk. Splitting plain + cache from native, as the brief suggested, would have put the cheap part alone in the second PR and left the first PR at its largest.
- **Layout (Redisson's, verified in the sources):**
  - The multimap hash lives at the raw name (`Key::new(core, name)`, no tag), like `HashMap`. It maps each codec-encoded key to `hash128_base64(encoded key)` (Redisson's `Hash.hash128toBase64`), stored as a raw UTF-8 string, not codec-encoded.
  - The values of a key live in a list or set at `suffix_name(name, &hash)`, which is `{name}:<hash>`, or `<name>:<hash>` when the name already has `{`.
  - The cache variants add a zset `suffix_name(name, "redissun_list_multimap_ttl")` or `"redissun_set_multimap_ttl"`. Its members are encoded keys and its scores are deadlines in client Unix ms. The expire tag is `redissun__expiretag`, as in `hash_map_cache/scripts.rs`.
  - The JSON key `"key"` hashes to `IKm9EBQhlzpVIBxUXDHBWw` (the vector in `tests/it/hash_map.rs`).
- **Names (`javap` 4.8.0 → redissun):**

- **The view methods** (`keySet().contains/remove/size/clear`, `entries().contains/remove`, `values().contains/size`) are `contains_key`, `remove_many`, `key_len`, `clear`, `contains_entry`, `remove`, `contains_value` and `len`. The migration guide lists them.
- **`putAll(Multimap)` is not ported.** `javap org.redisson.api.RMultimap` (4.8.0) has no such method, only `putAll(K, Iterable)`. The spec line is recorded from memory, and the parity rule (keep what Redisson has, drop what it lacks) decides. `extend(&k, values)` is `putAll(K, Iterable)`.
- **Handles: the methods of `Vec`/`HashSet` that keep the multimap's key index right, plus reads and index writes.** The rest of `RList`/`RSet` (set algebra, `move_to`, `pop`/`random` on sets, sort, distributed iterators, `tryAdd`) goes through `as_vec()`/`as_set()`, which return the raw object on the values key. Their rustdoc warns: "writes through it do not add the key to the multimap or check its TTL, as with Redisson's inherited `RList`/`RSet` methods".

  Both handles also have `name(&self) -> &str` (the values key) and `as_vec()`/`as_set()`. They do not implement `Object`: Redisson throws `UnsupportedOperationException` for `expire`, `rename` and `remainTimeToLive` on them.
- **Expired keys in the cache variants follow Redisson.** Reads of one key (`get_all`, `contains_key`, `contains_entry`, the handle) and `contains_value` hide an expired key at once. `len`, `key_len`, `keys_to_vec`, `remove_from_all_keys` and the streams count it until the clean-up task removes it, as Redisson's unoverridden `size`/`keySize`/iterators do. This is documented, not changed.
- **Native TTLs:**
  - `expire_key(&k, d)` runs Redisson's script: `HPEXPIRE` on the field, then `PEXPIRE` on the values key with the same ms.
  - `expire_key(&k, ZERO)` runs `NATIVE_PERSIST_KEY` (D3): `HPERSIST` + `PERSIST`, `true` when the key exists. Redisson's `hpexpire 0` deletes the field and leaves the values key behind.
  - `extend` keeps the TTL (D2). `replace_values`/`set_values` make the key permanent, because Redisson's scripts `HSET` the field and recreate the values key. This is documented.
  - Only `expire_key` needs Redis 7.4 (`support::require(&key, Needs::FieldTtl)` before the write). Every other method runs on 6.2.
- **Cache TTLs:** `expire_key(&k, d)` sends `ARGV[1] = now_millis() + millis(d)` (client clock, Redisson). `ZERO` sends `ARGV[1] = 0`, which takes the script's own `zrem` branch, so no Lua changes. It returns `false` on a missing key.
- **The clean-up task** is scheduled in the cache types' `new`, like `HashSetCache`. Task name `format!("redissun__multimap_eviction:{timeout}")` (the ttl zset name, which holds the shape, so a list and a set cache under one name each get a task), keys `[name, timeout]`, arguments `fn(_) -> vec![now_millis, KEYS_LIMIT]` (Redisson's `MultimapEvictionTask` has no latch). The script is `CACHE_EVICT` (D1).
- **Retry:** scripts sent with Redisson's `evalWriteNoRetryAsync` go through `Core::eval_once`: list `put`, `putAll`, `replaceValues`, `fastReplaceValues`, and their cache/native variants. Every other script goes through `eval`. Single commands (`LLEN`, `SCARD`, `SISMEMBER`, `LRANGE`, `SMEMBERS`, `HLEN`, `HKEYS`, `HSCAN`) go through `Key::read`.
- **`Object`:** `HasKey` gets two defaulted hooks: `fn persist_args(&self) -> Vec<Bytes>` and `fn rename_script(&self, new_name: &str) -> Option<(&'static Lua, Vec<String>, Vec<Bytes>)>`. `Object::rename` uses `rename_script` when it is `Some`. `Key::del_with` changes from `removed == 1` to `removed > 0`, because Redisson's multimap `delete` returns the number of deleted keys (`EVAL_BOOLEAN_AMOUNT`). Check that the one other user (`local_cached_map.rs` `del_script`) returns only 0/1. Cluster: as for every multi-key object, `rename` works only to a name in the same slot (documented).
- **Events:** `MultimapEvent<K>` (`#[non_exhaustive]`): `Put { key: Option<K> }` (`hset`, `MapPutListener`), `Removed { key: Option<K> }` (`hdel`, `MapRemoveListener`), `ValueAdded { name: String }` (`rpush`/`sadd` on a values key, `ListAddListener`/`SetAddListener`), `ValueRemoved { name: String }` (`lrem`/`srem`, `ListRemoveListener`/`SetRemoveListener`), `Deleted`, `Expired`. `MultimapEventKind` has the same six. `MultimapEvents<K, C>` wraps a `MapEvents<K, C>` subscribed to `[Put, Removed, Deleted, Expired]` and adds `__keyevent@*:rpush`/`lrem` (list) or `sadd`/`srem` (set) subscriptions. Those keep a message when `payload.starts_with(suffix_name(name, ""))`, as Redisson's `m.startsWith(prefix)` filter does. `recv()` and `into_stream()` work as on `MapEvents`.
- **Not ported (as on the other objects):** `sizeInMemory`, `copy` (Redisson throws), `renamenx`, `expireAt`/`expireIfSet`/…, `RDestroyable.destroy` (the clean-up task stops with the client), `mapReduce`, batch views (spec non-goal).

### Recorded Redis-side deviations (each `static` carries `/// Deviation from Redisson: …`; the PR lists them)

| # | Script | Change | Reason |
|---|---|---|---|
| D1 | `CACHE_EVICT` (`MultimapEvictionTask.execute`) | `'{' .. KEYS[1] .. '}:' .. v` → `local prefix = string.find(KEYS[1], '{', 1, true) and (KEYS[1] .. ':') or ('{' .. KEYS[1] .. '}:')` and `prefix .. v` | Redisson's prefix is wrong for names that contain `{`. It leaks the values keys, and on a cluster it fails with a non-local key. The new prefix is `suffix_name` in Lua |
| D2 | `NATIVE_LIST_PUT_ALL`, `NATIVE_SET_PUT_ALL` | `hset` → `hsetnx` | `HSET` clears the field's TTL while the values key keeps its own. The field always holds the same hash, so `hsetnx` writes the same data |
| D3 | `NATIVE_PERSIST_KEY` (new) | `hpersist` field + `persist` values key | `expire_key(&k, ZERO)` means "no TTL" crate-wide |
| D4 | `CACHE_RENAME` | Redisson's `renameAsync` + `rename` of the ttl zset when it exists | Redisson's cache does not override `rename`, so it drops every key TTL and leaks the old zset |
| D5 | `CACHE_LIST_PUT`, `CACHE_SET_PUT`, `CACHE_*_PUT_ALL`, `CACHE_*_REPLACE_VALUES`, `CACHE_*_FAST_REPLACE_VALUES`, `CACHE_EXPIRE_KEY` | when `hsetnx`/`hset` returns 1 (a new key), `zrem` the key from the ttl zset. The put and replace scripts also take `now` (ARGV[3], client clock; the values move to ARGV[4]…) and start with `drop_expired_key!`: when the field exists and its score is `<= now`, `del` the values key and `zrem` the score, so the key restarts clean without a TTL (the replace scripts then return no old values). `CACHE_EXPIRE_KEY` takes `now` (ARGV[3]) and returns 0 for such a key without re-arming it | `remove`, `remove_many` and `remove_from_all_keys` leave the score behind, and the clean-up can be up to 30 min away. A key inserted again later would then read as expired, and the clean-up would delete its new values. A write to an expired key that is not yet cleaned up went into the hidden values and was lost at the clean-up, and a later `expireKey` revived the old values (found in the final review of PR 3b) |
| D6 | `LV_LAST_INDEX_OF` | `lrange KEYS[1]` → `KEYS[2]`; `ARGV[1]` → `ARGV[3]` | Redisson's script reads the zset as a list (`WRONGTYPE`) and compares the timestamp |

| D8 | (routing, no Lua) cache handle `push`/`extend`/`insert` | go through the multimap's put scripts, not raw `RPUSH`/`SADD` | Redisson's cache handle does not add a new key to the hash, so its values are invisible to `keys`, `len` and the clean-up |
| D9 | (routing, no Lua) cache handle `clear` | `CACHE_*_REMOVE_ALL` instead of `RedissonList/SetMultimapValues.deleteAsync` | Redisson's version deletes nothing when the key has no TTL score and never `hdel`s |
| D10 | `LIST_VALUES_REMOVE_ALL` (`RedissonListMultimap.InnerList.removeAllAsync`) | `lrem(...) == 1` → `lrem(...) > 0` | `LREM` with count 0 returns the number removed, so for a value that occurred more than once Redisson's script returns `false`, and when that empties the list it keeps the key in the hash with no values (found in the final review of PR 3a) |
| D11 | `LV_REMOVE_ALL` (`RedissonListMultimapValues.removeAllAsync`) | `lrem(...) == 1` → `lrem(...) > 0`, the D10 fix | the same `LREM` count bug as D10 in the cache handle, so handle `remove_values` means the same in every mode (found in Task 12) |

## Global Constraints

- `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::todo, clippy::unimplemented)]`. Tests may unwrap.
- Lua: every `static` in `multimap/scripts.rs` is copied verbatim from the method named in the table. Each has a `/// Redisson<Class>.<method>` comment. The only edits are `redisson__expiretag` → `redissun__expiretag`, D1–D7, D10 and D11. No other new Lua.
- Data: as in "Layout". Values keys are never codec-encoded names. The ttl zset is `suffix_name(name, "redissun_{list|set}_multimap_ttl")`. Redisson and redissun clients share the hash, the values keys and the per-key locks.
- Minimum server: 6.2 for everything, except native `expire_key` (Redis 7.4 / Valkey 9, `HPEXPIRE`), checked before the write with `Error::Unsupported("ListMultimapCacheNative needs Redis 7.4 or newer (HPEXPIRE)")` (or `SetMultimapCacheNative`).
- Bounds as on `HashMap`: `K: Borrow<Q>`, `V: Borrow<W>`, `Q/W: Serialize + ?Sized + Sync`. Values iterators are `impl IntoIterator<Item = &'a W>`, encoded before the first `.await`.
- No private trait in a public bound. `Shape`, `Mode`, `Ops` and `Slot` are `pub(crate)` at most.

## Review Focus

1. **Hash-tagged names and Redis Cluster.** `{t}:m` keeps its values at `{t}:m:<hash>` and its ttl zset at `{t}:m:redissun_list_multimap_ttl`. Every script runs on a 3-master cluster without a cross-slot error, and the clean-up deletes the values keys of a tagged name (D1). Pinned in Task 8 (`every_operation_runs_on_a_cluster`) and Task 11 (`clean_up_deletes_values_of_a_tagged_name`).
2. **Empty inputs.** `extend(&k, [])` must not leave a key with no values, which Redisson's `hset` would. `replace_values(&k, [])` and `set_values(&k, [])` remove the key and return or drop its old values. `remove_many(&[])`, `remove_from_all_keys(&[])` and handle `remove_values([])` send nothing and give `0`/`false`. `contains_all([])` is `true`. Pinned in Task 2 (`empty_inputs_send_nothing_and_leave_no_key`) and Task 5 (`handle_empty_inputs`).
3. **A key whose values were emptied by an index write.** `pop`, `remove(i)` or `trim` on the handle, or list `remove_from_all_keys` (which never `hdel`s): `contains_key` is `false`, `get_all` is empty, `iter`/`values` skip the key, and `key_len`/`keys` still count it until `remove_all`/`remove_many`, as in Redisson. Documented. Pinned in Task 5 (`index_writes_can_leave_an_empty_key_like_redisson`).
4. **Native TTL consistency.** After `expire_key(k, d)`, `extend(k, …)` keeps both TTLs (D2). After expiry, `len`, `key_len`, `contains_key` and `get_all` all show the key gone. `expire_key(k, ZERO)` makes both permanent (D3). On Redis 7.2, `expire_key` is `Error::Unsupported` and writes nothing, while every other method works. Pinned in Task 7 (`native_extend_keeps_the_ttl`, `native_expiry_removes_field_and_values_together`, `native_zero_ttl_clears_both`, `native_expire_key_needs_redis_7_4`).
5. **Cache: expired but not yet cleaned, and re-inserted keys.** Per-key reads hide an expired key at once, while `len` and `key_len` count it until the clean-up runs. A key whose values were removed with `remove`/`remove_many` and that is inserted again after its old deadline reads as live, with no TTL (D5). `expire_key(k, ZERO)` clears the TTL. A put or replace over an expired key that is not yet cleaned up starts the key clean, and `expire_key` on it is `false` (D5). Pinned in Task 10 (`expired_keys_hide_from_key_reads_but_count_until_cleaned`, `a_reinserted_key_starts_without_the_old_ttl`, `zero_ttl_clears_a_key_ttl`) and the 3b fix pass (`writes_over_an_expired_key_start_clean`, `replace_values_over_an_expired_key_returns_no_old_values`, `expire_key_on_an_expired_key_is_false`).

New experimental `ListMultimapCache` and `SetMultimapCache`: Redisson's multimap caches with a TTL per key (`expire_key`) kept in a ttl zset with Redisson's layout and the redissun prefix, Redisson's clean-up task, and TTL-aware value handles. Completes #3 (six multimaps).

## Changelog
### Added
- `ListMultimapCache`, `SetMultimapCache` (experimental; `client.list_multimap_cache(name)`, `client.set_multimap_cache(name)`): every `ListMultimap`/`SetMultimap` method, plus `expire_key(&k, ttl)`; reads of one key and the value handles hide expired keys at once, the clean-up task removes them.

### Behaviour that differs from Redisson on purpose
- `expire_key(&k, Duration::ZERO)` removes the key's TTL.
- A put or replace over a key that has expired but is not yet cleaned up starts the key clean (only the new values, no TTL; `replace_values` returns no old values), and `expire_key` on such a key returns `false` without reviving it. Redisson writes into the hidden values, loses them at the clean-up, and revives the old values on a later `expireKey`.
- The value handle's `push`/`insert`/`extend` add a new key to the multimap and its `clear` removes the key, as on the plain multimaps; Redisson's cache handle writes the raw list or set only.

### Redis-side deviations from Redisson (recorded per CLAUDE.md)
- D1 `CACHE_EVICT`: the values-key prefix is computed like `suffix_name`, so names with `{` are cleaned up (Redisson's `'{' .. KEYS[1] .. '}:'` misses their keys and fails on a cluster).
- D4 `CACHE_RENAME`: Redisson's rename script plus a rename of the ttl zset, so key TTLs survive `rename`.
- D5 `CACHE_*_PUT`, `CACHE_*_PUT_ALL`, `CACHE_*_REPLACE_VALUES`, `CACHE_*_FAST_REPLACE_VALUES`: a key that is new to the hash drops a stale score from the ttl zset; the scripts take the client clock and first delete the values and score of an expired key that is not yet cleaned up. `CACHE_EXPIRE_KEY` takes the client clock and returns 0 for such a key without re-arming it.
- D6 `LV_LAST_INDEX_OF`: reads the values list and the value argument (Redisson's script reads the zset and the timestamp).
- D7 `LV_REMOVE`: returns the `LREM` count, so `remove_value_n` and `remove_value_all` return how many were removed.
- D11 `LV_REMOVE_ALL`: `lrem(...) > 0` instead of `== 1` (the D10 fix of PR 3a), so the cache handle's `remove_values` reports a value that occurred several times.
- (Routing, no Lua) D8: the cache handle's `push`/`insert`/`extend` go through the multimap's put scripts; D9: its `clear` runs `CACHE_*_REMOVE_ALL`.
- Every other script is Redisson's, verbatim.
