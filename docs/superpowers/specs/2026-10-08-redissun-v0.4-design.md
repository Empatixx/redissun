# redissun v0.4 design

## Goal

Four additions, chosen by the user: `Topic` (pub/sub messages), blocking pops on `VecDeque`, `RwLock`, and `HashMapCache` (a map with a time limit on each entry).

## Topic

`client.topic::<M>(name)` returns a `Topic<M, C>`. It has no key to expire or rename, so it is not an `Object`.

- `publish(&m) -> usize` sends the message and returns how many Redis connections got it (`PUBLISH`). All subscribers of one client share one connection.
- `subscribe() -> Subscriber<M, C>`. `Subscriber::recv().await` returns the next message. `Subscriber::into_stream()` returns a `Stream` of `Result<M>`.
- `subscriber_count() -> usize` (`PUBSUB NUMSUB`) counts the subscribers of all programs.
- The Redis channel is the plain topic name, so programs that are not redissun can publish and subscribe too.
- A subscriber gets only the messages published after `subscribe` returned. It does not see older ones.
- Each subscriber has a buffer of 256 messages. A slow subscriber that falls behind gets `Error::Lagged(n)` once, with the number of missed messages, and then continues with the newest ones.
- Dropping the last `Subscriber` of a channel unsubscribes from Redis.
- `subscribe` waits for a round trip (`PING`) after `SUBSCRIBE`, so a message published after it returns is never missed.

How it is built: the existing `PubSub` already shares one Redis subscription per channel with a reference count and wakes waiters. Each channel entry also gets a `tokio::sync::broadcast` sender. The dispatcher sends the payload bytes to it. Lock, semaphore and latch channels ignore the payload.

## Blocking pops on VecDeque

- `pop_front_wait().timeout(d) -> Option<V>` and `pop_back_wait().timeout(d) -> Option<V>` wait up to `d` (`BLPOP`, `BRPOP`).
- `pop_front_wait() -> V` and `pop_back_wait() -> V` wait without a limit. (Since 0.5 all waiting calls share this shape: await them, or add `.timeout(d)`.)
- A blocking command ties up its Redis connection, and a pooled connection is shared with other calls, so a blocked pop would stall them. So each blocking call first tries a normal pop. Only when the deque is empty does it open its own connection, block on it, and close it again.
- Dropping a pending pop unblocks and closes its connection (`CLIENT KILL ID`, then `QUIT`). If Redis had already handed over an element at that moment, the element is lost. Docs say: use the `_for` methods for time limits and not `tokio::time::timeout`.
- `timeout` must be positive. Zero is `Error::Config`. It is sent as fractional seconds.

## RwLock

`client.rw_lock(name)` returns a `RwLock`. Any number of readers or one writer. Names follow `tokio::sync::RwLock`.

- `read()`, `try_read()`, `write()`, `try_write()`; `read()` and `write()` take `.timeout(wait)`. Guards are `RwLockReadGuard` and `RwLockWriteGuard`. Both have `unlock(self)` and release in the background when dropped.
- `is_write_locked()` and `force_unlock()`.
- Owners are the client plus the tokio task, and holds are reentrant, like `Lock`. A task that holds the write lock may also take the read lock. A task that holds the read lock and asks for the write lock waits forever (or times out). It is not upgraded.
- A watchdog renews the lease of every hold, like `Lock`. `RwLockOptions` is not added now. `_for` methods cover the wait time, and the lease is the client's `lock_lease`.
- Readers are not blocked by waiting writers, so a steady stream of readers can starve a writer. Docs say so.

The scheme is taken from Redisson's `RedissonReadLock` and `RedissonWriteLock`. The lock is one hash `{name}`:

| Field | Meaning |
|---|---|
| `mode` | `read` or `write` |
| `<owner>` | read hold count of the owner |
| `<owner>:write` | write hold count of the owner |

Every read hold also has a key `{name}:<owner>:rwlock_timeout:<n>` with its own lease. The hash lease is the longest of them. When a reader unlocks, the script recomputes the longest remaining hold lease. If none is left, the hash is deleted, so a crashed reader stops blocking writers when its lease ends. A write hold renews the hash lease directly. Release by the last reader and release by the writer publish on `redissun__unlock__{name}`, and waiters retry.

## HashMapCache

`client.hash_map_cache::<K, V>(name)` returns a `HashMapCache<K, V, C>`. It works like `HashMap`, and each entry can have its own time to live.

- `insert(&k, &v)` has no time limit. `insert(&k, &v).ttl(ttl)` expires after `ttl`: `insert` returns a builder that implements `IntoFuture`, so it can be awaited directly or after `.ttl(..)`. Both return the previous live value.
- `insert_nx(&k, &v) -> bool` inserts only when there is no live entry. It takes `.ttl(..)` too.
- `get`, `remove`, `contains_key`, `len`, `is_empty`, `clear`, `iter`, `keys`, `values` behave like `HashMap` but never show an expired entry. They are `async`, because they evict expired entries first.
- `entry_ttl(&k) -> Option<Duration>` is the time left of one entry. `None` means no limit or no entry.
- `evict_expired() -> usize` deletes expired entries now and returns how many.

Keys: hash `{name}` holds the values and sorted set `{name}:expires` holds `field -> expiry time in ms`. Entries without a limit are not in the sorted set. Time comes from the Redis server (`TIME` inside the script), so clients with different clocks agree. Expiry is lazy: every script checks the entries it touches and deletes the expired ones. `iter`, `keys` and `values` call `evict_expired` first. `len` counts only live entries and deletes nothing. There is no background task, so an entry nobody touches stays in memory until someone calls `evict_expired`, `len` or `iter`, or the map is cleared. Docs say so.

## Object for several keys

`HashMapCache` owns two keys, which is the second multi-key object after `RateLimiter`. `HasKey` gets `fn companions(&self) -> Vec<String>` with an empty default. The blanket `Object` impl then:

- `del` deletes the main key and the companions.
- `exists` and `ttl` look at the main key.
- `expire` and `persist` apply to the main key and the companions.
- `rename` returns `Error::Unsupported` when there are companions.

`RateLimiter` keeps its hand-written impl for now. `RwLock` and `Topic` are not `Object`s.

## Errors

New variant `Error::Lagged(usize)`.

## Naming

All names are Rust names where Rust has one: `RwLock` (tokio), `HashMapCache` (`HashMap` plus the Redisson idea of a cache), `Topic` (a Redis/Redisson term with no Rust type), `Subscriber`.

## Testing

Integration tests against real Redis for every method:
- Topic: message round trip, several subscribers, late subscriber sees nothing old, lag error, cleanup observed with `PUBSUB CHANNELS`, interop with a raw `PUBLISH`, `subscriber_count`.
- Blocking pops: returns at once when an element exists, waits and wakes on a push from another task, times out, the other pool connections are not stalled during a wait, FIFO order for several waiting consumers, each element goes to exactly one consumer.
- RwLock: many readers at once, a writer excludes readers and writers, reentrancy, write-to-read downgrade, timeouts, wake-up faster than the fallback poll, a crashed reader (lease ends) stops blocking, drop releases.
- HashMapCache: expiry by server time, `insert` without a limit clears an old limit, `insert_nx` over an expired entry, `len` and `iter` skip expired entries, `evict_expired`, `Object` methods on both keys.

## Out of scope

Pattern topics, `BlockingQueue` as a separate type, priority queues, `FairLock`, `MultiLock`, writer preference, idle timeouts on cache entries, a background evictor, entry listeners, `Object` for `RateLimiter` via companions.
